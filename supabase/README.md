# Supabase — سير العمل

## الترتيب (تُطبَّق بالترتيب في SQL Editor أو عبر supabase CLI)
1. `0001_schema.sql` الجداول + المحفّزات + `can_read_task()`.
2. `0002_policies.sql` المنح الصريحة + RLS + واجهتا العميل (`client_tasks`, `client_task_parts`) + النشر للـ Realtime.
3. `0003_invitations.sql` نظام الدعوات: جدول `invitations` + دالة `invite_user()` + محفّز `on_auth_user_created`.
4. `0004_rpc.sql` عمليات ذرية (`create_client`, `create_task`) + محفّزات تنظيف المحادثات عند حذف مهمة/عميل.
5. `seed/production.sql` مرة واحدة: المنظمة + دعوة أول إدارة (بدّل `<ADMIN-EMAIL>` و`<ADMIN-NAME>` قبل التشغيل).

## قاعدة العميل (2026-10-27)
العميل **لا يقرأ جدولي `tasks` و`task_parts` أبداً**. يقرأ فقط الواجهتين `client_tasks` (عنوان، نوع، تواريخ، اعتماد) و`client_task_parts` (اسم المرحلة + تمت/لم تتم). محادثة المهمة `task:<id>` للإدارة والمبدعين المشاركين فقط. أي إضافة مستقبلية للعميل = واجهة جديدة بحقول محددة، لا سياسة على الجدول.

## كيف يدخل عضو جديد (دعوة فقط — لا تسجيل مفتوح)
1. الإدارة في همشة: `invite_user(email, role, client_id, name)` (للعميل `client_id` إلزامي، للفريق ممنوع). يُسجَّل في `invitations` بصلاحية ٧ أيام؛ إعادة الدعوة لنفس الإيميل تحدّث الدعوة المفتوحة وتمدّدها.
2. إرسال الإيميل: زر «ادعُ عضواً» في همشة (Edge Function `invite-member`) يسجّل الدعوة ويرسل البريد معاً. البديل اليدوي: صف في `invitations` + Authentication → Users → **Invite user**.
3. لما يقبل الشخص الدعوة ويضع كلمة سره، يُنشأ صف في `auth.users` → المحفّز `handle_new_user()` ينشئ `profiles` + `user_settings` **من الدعوة فقط** ويعلّمها مقبولة. بلا دعوة مفتوحة = يُرفض إنشاء الحساب (الإيميل المجهول يطلع له «Database error saving new user» — هذا مقصود).
4. في لوحة Supabase قبل أول دعوة: Authentication → Providers → Email: **أطفئ «Allow new users to sign up»**، فعّل تأكيد الإيميل وحماية كلمات المرور المسرّبة. وفي Authentication → URL Configuration: Site URL = `https://hamsha.studio` و Redirect URLs تشمل `https://hamsha.studio/welcome` (+ `http://localhost:5173/welcome` للتطوير) — رابط الدعوة ورابط «نسيت كلمة المرور» يفتحان شاشة `/welcome` حيث يختار الشخص كلمة مروره ويدخل.
5. إيميل واحد = حساب واحد = منظمة واحدة (فهرس فريد على `profiles` و على الدعوات المفتوحة عبر كل المنظمات).

ملاحظة: المحفّز يعمل بدور `supabase_auth_admin`، لذلك صلاحية تنفيذ `handle_new_user()` ممنوحة له فقط.

## المستودع الحقيقي `src/data/supabase.ts`
- `VITE_BACKEND=supabase` + `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` (و`VITE_DEMO=false` في الإنتاج).
- الفريق: يقرأ الجداول (RLS تفلتر الصفوف) ويستقبل Realtime على messages/tasks/task_parts/profiles/clients/projects ويعيد التحميل مجمّعاً.
- العميل: يقرأ الواجهتين فقط، ويعيد التحميل كل دقيقة + Realtime على الرسائل.
- كل كتابة ترجع للشاشة بعد تأكيد قاعدة البيانات مباشرة (طلب واحد): الصف المؤكد يُدمج في اللقطة المحلية فوراً، وإعادة التحميل الكاملة تصير في الخلفية للمطابقة. ما يُعرض شيء قبل تأكيد القاعدة، فلا يوجد «تراجع». تحديث المهمة مشروط بـ `version` (لو تغيّر عند غيرك ترجع «stale» وتُعاد القراءة).
- المنطقة: Supabase ما عنده منطقة في الخليج (قائمة المناطق الرسمية 2026-10-27)؛ الأقرب Mumbai (ap-south-1) أو Frankfurt (eu-central-1) — تُقاس من شبكة هوامش قبل إنشاء مشروع الإنتاج.
- المبدع يرسل على `task_parts` حقل `done` فقط (القاعدة ترفض غيره).
- الإنشاءات المركبة عبر RPC (`create_client`, `create_task`)؛ الحذف يعتمد على cascade + محفّزات تنظيف المحادثات.
- **كُتب قبل وجود المشروع (2026-10-27)، راجعه Codex، وفُحص بالأنواع فقط.**

## أول تشغيل حي (قائمة الفحص)
1. نافذة خاصة بلا جلسة → شاشة الدخول تظهر فوراً (بلا خطأ تحميل).
2. تطبيق 0001→0004 ثم `seed/production.sql` بإيميل الإدارة → Invite user من اللوحة → الرابط يفتح `/welcome` → كلمة مرور → الدخول كإدارة.
3. من SQL Editor: `select invite_user('creative@…','creative')` و `select invite_user('client@…','client','<client-id>')` → Invite user لكل واحد → دخولهم → يشوف كل واحد ما له فقط. وجرّب إيميلاً غير مدعو: يجب أن يُرفض.
4. إنشاء عميل + مشروع + مهمة + جزء + رسالة من الواجهة، وقارن عدد الصفوف في الجداول.
5. نافذتان بحسابين: تعديل نفس المهمة بنفس الإصدار → الثانية «stale»؛ حذف مهمة لها محادثة → المحادثة تختفي؛ فك ارتباط حساب عميل من لوحة الإدارة.
6. Realtime: رسالة من نافذة تظهر في الثانية؛ العميل يرى مهمة جديدة خلال دقيقة.
7. «نسيت كلمة المرور» من شاشة الدخول → الإيميل → `/welcome`.

## «ادعُ عضواً» (2026-10-28)
- لوحة الإدارة → «ضغط الفريق» → زر **ادعُ عضواً**: بريد + اسم + دور (+ العميل إن كان الدور عميلاً).
- `supabase/functions/invite-member/index.ts` (Edge Function، verify JWT مفعّل): تستدعي `invite_user()` **بتوكن المستدعي نفسه** (القاعدة تقرر من هو الإدارة من `profiles.role`)، ثم ترسل بريد الدعوة بمفتاح الخدمة عبر `auth.admin.inviteUserByEmail` مع `data = {role, name, client_name}` **للعرض في القالب فقط** (RLS لا تقرأ `user_metadata` أبداً) و`redirectTo = https://hamsha.studio/welcome` (ضمن Redirect URLs).
- الحالة صادقة: `sent:true` · `sent:false` مع `already_registered` (حساب موجود → «نسيت كلمة المرور؟») أو `send_failed` (الصف سُجّل، أعد المحاولة).
- قالب البريد «Invite user» في اللوحة يقرأ `{{ .Data.role }}` / `{{ .Data.name }}` / `{{ .Data.client_name }}` ويعرّب الدور؛ بدون metadata (دعوة من اللوحة مباشرة) يعرض النص العام.
- النشر: اللوحة → Edge Functions → `invite-member` (لصق محتوى الملف). المتغيرات `SUPABASE_URL/ANON_KEY/SERVICE_ROLE_KEY` تضخّها Supabase تلقائياً؛ `HAMSHA_SITE_URL` اختياري.
- الاختبار: `tests/smoke-invite.mjs` (mock): زر → نافذة → تحقق البريد → إرسال → toast → العضو يظهر → القائمة المعلّقة + «أعد الإرسال» → تكرار البريد مرفوض.
- **الدعوات المعلّقة** (0005): `pending_members()` (security definer، للإدارة فقط، منظمتها فقط) = ملف موجود + `auth.users.email_confirmed_at` فارغ. تظهر في اللوحة تحت زر الدعوة مع «أعد الإرسال» (نفس الدالة بـ `action: "resend"`؛ Auth يعيد دعوة غير المؤكَّد، والمؤكَّد يرجع `already_registered`).
- **Storage** (0006): حاويتان `client-logos` (قراءة عامة) و`attachments` (خاصة)؛ المسار `<org_id>/…`؛ القراءة لأعضاء المنظمة، الكتابة للإدارة والمبدعين، الحذف للإدارة. الملف يتخطى CI المحلي (لا storage schema) ويُطبَّق على Supabase فقط — لا واجهة رفع بعد.

## «السوشل» المرحلة ١ (0007 — 2026-10-28، مجلس 20261028-032546-200e، اختيار يوسف ٤)
- التدفق: `draft` (الفريق يرفع) → `sent` (الإدارة ترسل للعميل) → `approved` أو `changes` (قرار العميل) → `published` (الإدارة تلصق الرابط). أي نسخة جديدة ترجّع المنشور `draft` ولازم يُرسل من جديد — **الموافقة مربوطة برقم النسخة** ولا تنتقل.
- الجداول: `posts` (العميل، المهمة اختياري، المنصة instagram/tiktok/snapchat/linkedin/x، المقاس square/portrait/story، الحالة، `current_version`) + `post_versions` (صورة + نص **مجمّدان**، ملاحظة للعميل، القرار وملاحظته). رقم النسخة تعيّنه القاعدة (`post_versions_insert`)، والانتقالات يفرضها `posts_status_guard` (الإدارة فقط؛ الإرسال يحتاج نسخة؛ النشر يحتاج رابطاً؛ بعد «يبي تعديل» لا يُعاد إرسال النسخة نفسها).
- العميل: لا يقرأ الجدولين أبداً — واجهتان `client_posts` و`client_post_versions` (بلا أشخاص ولا حقول داخلية)، وكتابته الوحيدة `decide_post(version, decision, note)` (security definer: منشوره، الحالة `sent`، النسخة الحالية فقط، مرة واحدة، «يبي تعديل» يحتاج ملاحظة).
- الفريق: الإدارة كل شيء؛ المبدع ينشئ منشورات ونسخاً للعملاء الذين له مهمة معهم (`works_with_client`) ويقرأ منشوراتهم؛ لا يغيّر الحالة ولا يحذف.
- الملفات: حاوية خاصة `post-media` (صور حتى ١٠ ميجا) بمسار `<org>/<client>/<post>/<n>-<rnd>.<ext>`؛ القراءة للفريق وللعميل صاحب المجلد الثاني، الرفع للفريق، الحذف للإدارة. الواجهة تعرضها بروابط موقّعة (ساعة).
- Realtime: `posts` و`post_versions` منشوران؛ العميل يعيد التحميل كل دقيقة كالمعتاد.
- الاختبار: ٤٩ سطراً `[soc]` في `rls.sql` + `tests/smoke-social.mjs` (الدورة كاملة بالأدوار الثلاثة على mock). انظر ١.٥ أدناه.
- مؤجَّل عمداً: الفيديو، الملاحظة على ثانية/شريحة، المعتمد البديل، تنبيه الخمس ساعات، النشر التلقائي، الإحصاءات.

## «السوشل» ١.٥ (0008 — 2026-10-29، مجلس 20261029-021136-0526 بعد اختبار يوسف للمرحلة ١)
- **ثغرة مسدودة:** العميل كان يرى المسودات. الآن `client_posts` تخفي كل منشور حالته `draft`، و`client_post_versions` تعرض فقط النسخ التي أُرسلت فعلاً (`post_versions.sent_at` يختمه `posts_status_guard` عند الإرسال، ولا يُكتب من الواجهة أبداً). نسخة جديدة غير مرسلة لمنشور سبق إرساله لا تظهر. `decide_post` يشترط `sent_at` أيضاً. السحب إلى مسودة يخفي المنشور ونسخه كلها.
- **الكاروسيل:** `post_versions.image_paths text[]` مرتّبة (العنصر ٠ = الغلاف)، من ١ إلى ٢٠ صورة (حد إنستقرام منذ أغسطس ٢٠٢٤؛ الواجهة تحدّ حسب المنصة: X = ٤). المجموعة كلها مجمّدة مع النسخة؛ الصور المحتفَظ بها من النسخة السابقة تُعاد بمسارها نفسه بلا رفع جديد، والملفات لا تُستبدل أبداً.
- **حسابات العميل:** `client_accounts` (client_id, platform, handle بلا @, display_name, avatar_path, bio) — الإدارة تكتب، المبدع يقرأ حسابات عملائه، العميل يقرأ حساباته. `posts.account_id` يربط المنشور بحساب من نفس العميل ونفس المنصة (يفرضه `posts_consistency`). الصور الشخصية في الحاوية العامة `client-logos` تحت `<org>/<client>/accounts/`.
- **الواجهة:** معاينة «في الفيد» بالصورة الشخصية والمعرّف الحقيقيين، نقاط الكاروسيل وعدّاد «١/٥»، الضغط على التصميم يفتحه ملء الشاشة (أسهم ← → و Esc، تبديل داكن/فاتح للمعاينة فقط)، عبارة «معاينة قبل النشر» ثابتة. بلا شعارات رسمية للمنصات وبلا أرقام إعجابات/تعليقات/متابعين وهمية. بعد «يبي تعديل» تفتح لوحة المنشور على النسخة المرفوضة وملاحظة العميل أمام الإدارة، ونموذج النسخة الجديدة يبدأ بكل صورها ونصها.
- **الاختبار:** `[soc2]` + `[acc]` في `rls.sql` (١٨٣/١٨٣) + `tests/smoke-social.mjs` (٦٥ فحصاً على mock).
- مؤجَّل عمداً: الشبكة ٣×٣ مثل البروفايل، الفيديو، التنبيهات.
