# تحقق قبل التسليم — Hamsha

The rule: **never say «خلصت» on Hamsha without a fresh evidence line from `verify.sh --full` on the same code fingerprint.** No evidence = not done.

## Two levels
| When | Command | Time (measured 27 Oct 2026) |
|---|---|---|
| While working, after each change | `.claude/skills/verify-before-delivery/verify.sh --quick` | ~3 s: tsc · oxlint · unit · test-integrity |
| Before delivery / commit / push | `.claude/skills/verify-before-delivery/verify.sh --full` | ~70–135 s: quick + SQL/RLS + build + smoke on the built app |

`verify.sh` only *calls* the project's own checks (`npx tsc -b`, `npm run lint`, `npm test`, `npm run build`, `supabase/tests/run-ci.sh`). If a check needs to change, change it in the project — never copy its logic into this skill.

Isolation: private Postgres on port **54339** (own data dir) and preview on **5198**. Never 54329 / `hamsha_rls` / 5173 — other chats and another project (صغار مبدعون) use those. A lock (`/tmp/hamsha-verify.lock`, shared by every session) stops two runs at once; the preview port must belong to this run or smoke fails.

## The loop
1. Run `--full`.
2. Exit 0 → deliver with the evidence (below).
3. Exit 1 (❌) → read the named log in `$TMPDIR/hamsha-verify/`, fix the **cause** (never the test), then rerun **from step 1** — the whole gate, not just the failed step.
4. At most 3 fix attempts. Still failing → stop and tell Yousef plainly what is broken, what you tried, and what you think it needs. Do not deliver.
5. Exit 2 (متعذر: tool missing / port busy / another run) → this is not a pass and not a reason to retry blindly; fix the environment or report it.
6. Exit 3 (smoke flaky: failed once, passed on retry) → NOT a delivery yet: rerun `--full` once more; deliver only on a clean exit 0, and still mention «smoke تذبذب مرة» in the evidence. Two flaky runs in a row = treat as a failure and find the cause.
7. Exit 4 (code changed during the run) → evidence is invalid; rerun.

If the code you would need to fix belongs to another active chat (uncommitted work you did not write), do NOT fix it: hand the diagnosis to Yousef for that chat, and rerun after it is fixed.

## Evidence format (paste in the delivery message)
```
✅ tsc · lint 0 أخطاء (2 تحذيرات) · unit · SQL 91/91 · build · smoke 6/6 — نسخة <fingerprint> · <seconds> ث
ما تحققنا منه: <copy the line verify.sh prints, plus anything specific to this change>
```
The «ما تحققنا منه» line is mandatory. Today every UI test runs on the **mock** backend: real Supabase (login, `createSupabaseRepo`, Realtime, invite e-mails), mobile and Safari are NOT proven by this gate.

## Does the green prove what Yousef asked for? (anti false-reassurance)
Before delivering, map his request to the check that proves it:

| He asked for… | Proven by | If no check proves it |
|---|---|---|
| Who can see / change what (roles, clients, privacy) | SQL/RLS suite (`supabase/tests/rls.sql`) — must be **run**, never judged by reading | add a `t.run(...)` line, then `verify.sh --baseline` |
| Something a role sees or does on screen | a smoke test that first proves the item is **found**, then checks it | add/extend a smoke test in `tests/` (it must be in `npm test`) |
| Data saved | reload and read it back in the test | — |
| Works on the live Supabase / phone | **nothing yet** | say so in «ما تحققنا منه» |

A new check counts only after it has **failed once on deliberately broken code**: copy the project to the scratchpad (`rsync -a --exclude node_modules` + `cp -cR node_modules`), break the exact behaviour in the copy, run the check there → it must FAIL; then it must PASS on the real tree. Never use `git stash` / `checkout` for this (other chats keep uncommitted work here).

## Test integrity
`sql-baseline.txt` is the **approved test set**: checksums of every file that decides what "pass" means (`tests/*.mjs`, `supabase/tests/*` incl. the harness, seed and runners, and the `package.json` scripts that run them) + the 91 SQL test names. It is generated by `verify.sh --baseline`, never hand-written. Every run compares against it:
- a test file changed, added or deleted since approval (e.g. an `expect` loosened from `'error'` to `'none'`, the harness edited, `test:unit` turned into `true`) → ❌ until re-approved;
- a SQL test name deleted or commented out → ❌;
- the list missing or empty → ❌.

Re-approving (`--baseline`) is a deliberate act: it prints the changed files; check each change does not loosen an expectation, then say «حدّثت الاختبارات المعتمدة: <files> — <why>» in the delivery. Dropping a SQL test needs `--baseline --allow-remove` **and Yousef's OK**.

**Never make a test pass by changing the test or the mock data to match the bug.** If your fix touched `tests/`, `supabase/tests/` or `src/data/mock.ts`, list each of those changes in the delivery with one line of why.
`verify.sh` also warns on new `@ts-ignore`, `oxlint-disable`, `.skip(` and on deleted assertion lines in tracked files — explain each one in the delivery or undo it.

## Acceptance proof of this skill (27 Oct 2026)
Every case run on a scratchpad copy of the project; each one exited 1:
- client view leaking other clients' tasks + owner avatar shown to clients → `--full`: SQL ❌ (4 named failures) + smoke ❌ «week/day hide people»;
- one SQL `expect` loosened · one SQL test commented out · harness forced to pass · approved list emptied → `--quick`: integrity ❌;
- `--baseline` after deleting a test → refused without `--allow-remove`;
- a smoke test file deleted · `test:unit` replaced by `true` in package.json → `--quick`: integrity ❌;
- a deliberate `console.error` in the app → smoke-client-summary ❌ «no console errors» (all 6 smoke tests now fail on console errors).
Smoke passes only when the PASS lines are exactly the 6 expected test names; `build` also bundles the real Supabase configuration (placeholder URL/key).
The real tree passed `--full` in 71 s (SQL 91/91 · smoke 6/6). Reviews found 8 false-green holes in total (Gemini + a separate Claude reviewer: 4; Codex at 10:40 am: 4 more) — all fixed and re-proven above.
