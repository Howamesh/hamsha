# همشة (Hamsha)

تطبيق إدارة المهام والتقويم الداخلي لوكالة **هوامش**: تقويم رئيسي للمدير، مهام لكل مبدع، تقويم للعميل، محادثة فريق، تواريخ هجرية، وأوقات صلاة محجوزة في جدول المبدع.

## التقنية (قرار 2026-10-14 بعد مناظرة Claude × Codex)
- **الواجهة:** React 19 + TypeScript + Vite + Tailwind CSS v4 (مكوّنات بأسلوب shadcn).
- **الخلفية:** Supabase (Postgres + Auth + Realtime + Storage + RLS) — المرحلة الحالية تستخدم مخزناً مؤقتاً في المتصفح (`src/data/mock.ts`) بنفس الواجهة البرمجية.
- **الاستضافة:** Netlify (قرار المدير 2026-10-19) + GitHub (كل دفعة إلى `main` تُنشر تلقائياً). الدومين مشترى من Hostinger ويُربط بـ Netlify.
- **الهجري:** `Intl` المدمج بتقويم أم القرى. **الصلاة:** مكتبة `adhan` بطريقة أم القرى (+30 دقيقة للعشاء في رمضان).

## قواعد ثابتة
- كل نص في الواجهة يمر عبر `src/lib/i18n.ts` بالعربي والإنجليزي.
- نسبة الإنجاز تُحسب من الأجزاء ولا تُخزَّن.
- موعد المبدع = تسليم العميل − يوم واحد.
- عطلة نهاية الأسبوع: الجمعة والسبت. بداية الأسبوع: الاثنين (الأحد خيار للمستخدم).
- لا تُعدَّل تواريخ المهمة إلا من المدير (وستُفرض في قاعدة البيانات أيضاً).

## طبقة التحقق والصلاحيات
- `src/lib/validate.ts`: كل تاريخ/ساعة/وقت يُفحص قبل الحفظ (المخزن المؤقت والحقيقي).
- `src/store/session.ts`: حدود الصلاحيات في الواجهة (المدير فقط ينشئ ويحذف؛ المبدع يعلّم أجزاءه فقط ويرسل للاعتماد؛ العميل قراءة + محادثته).
- `supabase/migrations/0002_policies.sql`: نفس القواعد مفروضة داخل قاعدة البيانات (RLS) عبر `can_read_task()`.
- `src/components/ErrorBoundary.tsx`: أي خطأ عرض يظهر كرسالة مع زر إعادة تحميل بدل شاشة بيضاء.

## الاستضافة والبيئة
- `netlify.toml` + `public/_redirects`: إعداد Netlify (أمر البناء، Node 24، توجيه كل المسارات إلى `index.html`، ترويسات أمان).
- `.env.example`: المتغيرات المطلوبة. انسخه إلى `.env` ولا ترفع `.env` أبداً (مستثنى في `.gitignore`).
- `VITE_BACKEND`: `mock` (تجربة) أو `supabase`. أي قيمة أخرى أو خلفية غير مربوطة توقف التطبيق برسالة واضحة بدل ما يعمل بصمت على المخزن التجريبي.
- أزرار «جرّبه بدون حساب» تظهر فقط مع `mock` ويمكن إطفاؤها بـ `VITE_DEMO=false`.

## قبل تشغيل Supabase (قائمة الالتزام)
1. تشغيل `supabase/migrations/0001` ثم `0002` على مشروع تجريبي.
2. اختبار RLS بكل دور (مدير/مبدع/عميل): قراءة وكتابة بيانات الغير يجب أن تفشل. (هيكل الاختبار في `supabase/README.md`.)
3. دالة الدعوة `invite_user()` + `handle_new_user` (إنشاء الملف الشخصي والإعدادات من سجل دعوة موثوق، لا من بيانات التسجيل).
4. بذرة الإنتاج: منظمة + أول مدير (سكربت يُشغَّل مرة واحدة من الخادم).
5. نسخة احتياطية + تجربة استرجاع فعلية قبل أول دعوة.
6. تقارير الأخطاء (Sentry) في `main.tsx` و`ErrorBoundary`.
